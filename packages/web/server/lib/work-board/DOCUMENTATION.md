# Work board server module

The work board stores prompt cards in `work-board.json` under the OpenChamber data directory. It is server-owned state, separate from the message queue. Writes run serially within the server process and publish through a same-directory temporary file and atomic rename. A failed write leaves the prior board file in place.

The board is a **server-owned projection**: the lanes, order, queue state, live activity and the ask each session waits on that a client renders are derived once in the server process (`projection.js`) and handed out through `GET /api/work-board/snapshot`, rather than classified in every browser from its own history poll. Two tabs therefore agree, and a closed tab no longer stops the board from being right. The projection only reads; every write stays with the store and the queue runtime, so the board's own concurrency guarantees are unchanged.

`createWorkBoardProjection({ store, activity, listSessions, readQueueSnapshot, readQueueEnabled, readPendingRequests })` assembles one snapshot for a directory:

- **lanes / order** — each card's effective lane, in precedence order: (1) the build queue (a lease or waiting item owns its session's work), (2) the user's own placement (`placementAt`, until later session activity), (3) the session's own history (what the last turn actually did). A lane's order is its own rule — Done by newest completion first, the Plan lane by newest session start first, Build complete by newest finish first, To-do the stored order — with the cards the user dropped by hand moved to the place they named (`placementBefore`, null for the end of the lane). Only a card the user dropped is pinned: every other card keeps the lane's order, so a new completion sorts in at the top instead of landing under a stale arrangement. Done is the exception: it honours no drop, so the newest completion always leads it.
- **cards** — the directory's stored cards plus inherited cards: sessions in the directory the board has no stored card for, derived as `session:<id>`. Each card carries `status` (`known`, `unavailable`, `unknown`, `none`) and `availableActions`, the actions the server allows (`complete`, `acknowledge`, `startPlan`, `returnToTodo`, `remove`) so no surface re-derives reachability. The inherited list is bounded by the session window (`days`; `0` shows every session), so a card older than the window leaves only if it has no stored record. Delegated work is never a card: a session OpenCode reports as a subagent's child (`parentID`), or one running on a subagent-only agent, is left out of the inherited list, and a stored card that links such a session is left out with it.
- **sessionTitles** — each named session's own name, by session id. The names come from the same session-list read that builds the inherited cards: a client that has not loaded the session list itself still has a name to label a queue row or a linked card with, and a stored card's `text` is its brief, not the session's name. A session the read did not cover has no entry, so the client keeps its own name or its id fallback.
- **queue** — the queue runtime's build snapshot for the directory: waiting rows in dispatch order with positions, the running lease, forced builds, the project issue, preparation/commit state, and the project's own enablement (`enabled`, read independently of the queue snapshot so the toggle shows the saved choice even when the queue cannot be read). `known` is false when the queue snapshot failed; the client then reports the queue section as unknown rather than empty. A row, and the lease and forced entries, also carry the `model` the build was submitted with; the lease and forced entries carry the build's own `content`, so the board's tooltip shows why a card is queued or running.
- **activities** — true live activity per linked session, from `activity.js`.
- **waitingFor** — the ask each session waits on, by session id, from the session runtime's own list of pending permissions and forms (`getPendingBlockingRequestsSnapshot`), filtered to this board's sessions and queue entries. A session busy because it waits for the user's answer is not working (the space idle stop's decision of 2026-09-28), so the client must not paint it as running. It rides beside `activities` rather than inside it because an ask outlives a failed history read: a session whose history could not be read still reports what it waits for.
- **unavailable** — sessions whose live status or history could not be read this round; such a card is never treated as settled.
- **missing** — the subset of `unavailable` that OpenCode answered with its session-not-found body: the session does not exist, so no later read can succeed. The projection only names them; the runtime prunes their cards (below).

Session reads are failure-aware. A session list that fails or is malformed is a failure, not an empty list: the projection keeps the inherited cards of the last successful read for that directory and reports `inheritedAvailable`; only a directory with no successful read at all reports `inheritedAvailable: false` and no inherited cards.

Delegation is decided from the directory's agent catalogue (`listAgents`), read at most once a minute: an agent whose `mode` is `subagent` cannot be prompted directly, so it marks delegated work. A session the session-list read did not cover — a card older than the read, or any card while the read fails — is asked about with `readSession`, once, and the answer is remembered per session in a bounded map dropped by `forgetDelegated` when its record changes. An unknown catalogue or an unreadable session proves nothing, so its card stays.

`readWorkBoardSessions` passes the board directory as an explicit session-list
filter on every page. That endpoint is global without the filter, regardless of
the client's directory header. Returned sessions are also checked against their
own `location.directory` before the projection can inherit them into the board.
It returns delegated sessions with the rest — the projection, not the read,
decides what becomes a card.

`activity.js` (`createWorkBoardActivity`) keeps one answer per session in the server process. `readPage(sessionId, directory)` returns a real OpenCode v2 message page, whose flat records use `type` (mapped to `role` here) and carry no `sessionID` (supplied from the request). `listActiveSessionIds()` reads OpenCode's active-session channel; a read that fails is unknown, never idle, and every session in that round is reported unavailable. A failure whose error is OpenCode's `SessionNotFoundError` is reported as `missing` as well as unavailable: it is a deleted session, not a read that might succeed next round, and only that positive shape counts — the client's own transport and status errors stay retryable. History is reused only when a later read confirms the session's update time has not moved and nothing is running, so the projection passes each card's `updatedAt`. `invalidate(sessionId)` drops one session's history and `reset()` drops all of them.

`createWorkBoardProjectionRuntime` is the wiring boundary: `index.js` builds it with `readPage`, `readSessions`, `readActiveSessionIds`, `listAgents` (the directory's agent catalogue, whose `mode` marks subagent-only agents), `readSession` (one v2 session record by id, for a card the session list did not cover), `readPendingRequests` (the session runtime's pending asks), the queue snapshot and queue enablement readers, and passes its `projection` as `workBoardProjection` to `registerWorkBoardRoutes`. Its `snapshot(directory, options)` wraps the projection's own: when a read proves a session missing, it prunes that card through the store in the same call and drops it from `cards`, `lanes`, `order` and `placements`, so a response never carries a card the server has just deleted. The prune is the store's write, not the projection's, and a failed prune leaves the cards in place still reading as unavailable for the next read to retry. Its `processPayload(payload, directoryHint)` is the event lifecycle: called where translated server payloads flow (next to `sessionWorkRuntime.processPayload`), it invalidates the activity of the session the event names (and the inherited-card cache on `session.created`/`session.deleted`, and that session's delegation answer on `session.created`/`updated`/`deleted`) and returns the directory whose board changed. `permission.asked`/`permission.replied`/`form.created`/`form.settled` are handled the same way but invalidate nothing: the ask is not cached here, so those events only make the board re-read it. `index.js` then broadcasts `openchamber:work-board.updated` for that directory, which is what makes a Plan turn, an ask, or a card write reach every open board without a poll. `reset()` drops all caches on a runtime switch. A project with no wired projection answers `GET /api/work-board/snapshot` with 503, which is a real failure, not an empty board.

An ambiguous **Force** — a forced build whose prompt was not confirmed — is surfaced with `needsReview`, the `itemId` the Force targeted, and a recovery `action`. The queue runtime holds that state durably from before the prompt leaves, so it survives a restart, and the board neither hides it as a plain running build nor leaves it without resolution controls. A confirmed forced build stays display-only, and it carries `counts`: a build forced into the queue counts towards it, so the queue waits for it before the next build starts.

The store keeps the parsed card list of the last successful read in memory (`createWorkBoardStore`). Only this store process writes the file, so that list stays valid until a write replaces it, and a successful write makes the new list the one every later read sees. Without it every request re-parses the whole file, attachments included, and a card list can approach 50 MiB. A first read that finds malformed data is still a read failure: it caches nothing, so the failure never turns into a remembered empty board, and a later write cannot replace the file with a guess. `pruneMissing(directory, sessionIds)` is the one write for a card whose session no longer exists: it removes that directory's cards whose `sessionId` is in the caller's proven-gone set, in one serialized atomic write, and returns the session ids it pruned. An empty set removes nothing, and a card another directory owns is never touched, so the caller's evidence decides and the store only enacts it.

The authenticated API is registered before the generic OpenCode proxy:

- `GET /api/work-board/snapshot?directory=<path>&days=<n>` returns the projection described above. `days` is how many days back inherited sessions are read (`0` shows every session); a request without it uses the server's 30-day default.
- `GET /api/work-board?directory=<path>` returns `{ cards }` scoped to the resolved directory. Optional `sessionId` filters by the linked session, independently of its worktree directory. The session view uses this filter to restore saved briefs without reading unrelated attachment payloads. Omitting both filters returns the full list. Supplying both applies both filters. This plain list stays available for consumers that only need stored cards.
- `POST /api/work-board` accepts `{ directory, text, attachments }` and returns `{ card }` with status 201.
- `POST /api/work-board/sessions/:sessionId/todo` accepts `{ directory, sessionDirectory?, text, attachments }` and returns `{ card }`. The board directory and the session's worktree directory may differ. The queue runtime rejects queued, active, or uncertain work and holds queue dispatch while checking idleness and saving.
- `PATCH /api/work-board/:id` accepts `text`, `attachments`, `sessionId`, and/or `stage`, plus optional `expectedUpdatedAt`, and returns `{ card }`. When the expected version is stale, it returns 409 without changing the card. A client can offer the current card and retry an explicit overwrite against its new `updatedAt`.
- `PATCH /api/work-board/:id` also accepts `removeBrief: true`, alone, on a card that already links a session. It clears the text and attachments and stamps the card `briefRemoved`, so the board keeps its card and the session keeps its lane without the brief. The session view hides that entry, and parking the session again replaces the card with a fresh brief. Removal leaves `updatedAt`, `completedAt` and `viewedAt` alone, because the board's lane and completion rules read them. A content write against a removed brief is a 409.
- `PATCH /api/work-board/:id/viewed` acknowledges the card's current completion and returns `{ card }`. It is the only writer of `viewedAt`, requires no body, and leaves `updatedAt` alone so the completion's stale check still compares against the last real change. An unknown card is a 404; a card with nothing to acknowledge is returned unchanged. The acknowledgement lives on the server, so every client sharing the board clears the mark together.
- `POST /api/work-board/:id/placement` accepts `{ lane, expectedUpdatedAt?, before?, directory?, sessionId?, text?, completed? }` and returns `{ card }`. `lane` is `todo`, `plan`, `build`, or `done`. The placement and completion stamps come from the server's clock, never the request, so devices order by one source. `expectedUpdatedAt` is the version the client read: a card changed since then is a 409 instead of an overwrite, checked inside the serialized write. `before` names the card the moved one now sits in front of, `null` puts it at the end of the lane, and omitting it leaves that lane's stored order alone — except in Done, which stores no arrangement at all. `completed: true` marks a move into Done as a completion, so a card built again and completed again takes a fresh stamp; a card's first arrival is a completion either way. `directory`, `sessionId`, and `text` are the identity of an inherited card the board has no record for yet: its first placement creates the card, exactly as its first completion did, and any later placement of the same session's derived id is a 404 rather than a duplicate. An inherited card has no brief of its own — its `text` is the session's title, a label the projection adds — so the created record carries `briefRemoved` with empty text: the board keeps showing the title, and opening the card opens its session instead of a saved-draft edit. A drag writes the board and nothing else: it never starts a turn, and it cannot put a card into or take one out of the build queue.
- `DELETE /api/work-board/:id` removes the card and returns `{ ok: true }`.
- `POST /api/work-board/placement` accepts `{ directory, lane, targets }`
  and returns `{ placed, failed }`, the bulk form of one placement. Each target
  carries `id`, `updatedAt`, `text`, and optional `sessionId`; a `completed` flag on
  the body applies to every target, exactly as on a single placement. Each card's version
  check runs inside that card's own serialized write, so a target another device
  changed is failed with a 409 rather than overwritten, and one whose id belongs to
  another project is failed too. Cards are placed independently, so one conflict
  does not block the rest.

A card has `id`, `directory`, `text`, `attachments`, `createdAt`, `updatedAt`, and `stage`. `sessionId`, `completedAt`, `viewedAt`, `placementAt`, and `placementBefore` are optional. Stages are `todo`, `plan`, and `done`. Existing version 1 files remain readable without conversion; `placementOrder`, the retired whole-lane arrangement an older build stamped on every card of a lane, is read only so those files stay valid and is dropped on the next write. An attachment has `id`, `filename`, `mimeType`, `size`, and a validated base64 `dataUrl`. Text or at least one attachment is required. JSON bodies are limited to 50 MiB. The server checks base64 syntax, MIME consistency, and decoded size.

Only a placement can write `done`; generic PATCH cannot bypass the idle guard. Placement preserves saved text and attachments, but an inherited card's title is a label, never a saved brief: the first placement or completion that creates its record writes `briefRemoved` with empty text. Stored card ids,
directories, session links, and `updatedAt` must still match, and an inherited
session uses `session:<sessionId>` as its target id: the store creates its durable
card on first placement, and an existing link prevents a duplicate. A bulk target
whose `updatedAt` no longer matches, or whose id belongs to another project, is
reported as a failure rather than overwritten, and the remaining cards in the
batch are still placed. The server stamps `completedAt` on every completion: a
move into Done from another lane carries `completed: true`, and a card's first
arrival always completes. A card built again and completed again takes a new
stamp, so it leads Done and its completion mark returns. A move inside Done is an
arrangement, not a completion, and Done keeps no arrangement at all — it is
ordered by completion alone.
Returning to To-do clears the completion timestamp and any acknowledgement of it.

Promotion to `plan` requires a persisted session link. A card linked to one session cannot be linked to another. Clients persist the session link before sending and change stage only after the send succeeds. The card contents remain available after a failed send. A linked To-do offers an Open session action so the user can inspect an ambiguous send before submitting again. The client never automatically retries a linked card.

Parking uses one serialized store operation and one atomic file replacement to create or update a session-linked card. A failed write preserves the previous board and leaves no unlinked intermediate card. Repeating the latest notes does not append them again; attachment IDs deduplicate repeated uploads. Existing text and files are preserved when returning a card to To-do with no additional content.

The shared session transcript displays linked saved briefs directly from this
store, including cards saved before this display existed. It shows only cards
still in `todo`; a promoted card's text is a real user turn in the transcript, so
showing the card too would duplicate it. Parking never writes
an OpenCode prompt or synthetic message. The visible entry follows the saved
card through edits and removal; it does not change session activity or queue
admission.

Malformed persisted data is a read failure. It never becomes an empty board or gets overwritten by a later save. Store files use mode `0600` because they contain prompt text and attachment bytes. The store validates saved card shapes and duplicate ids as well as incoming content.

Stored stages describe the board's saved intent. The projection derives the Build queue lane from the project queue and live OpenCode status, and uses actual assistant/idle history for Plan and Build complete. Changing a model or agent selector alone does not change a card's lane. Parking a card sets `updatedAt`; a later real turn overrides that parking marker. Done ordering uses the card's manual completion timestamp, never the session's last update, and honours no drop, so the newest completion always leads it; Build complete orders by the settled turn's own time, falling back to the card's last change when history cannot be read. Every other lane's order is that rule, with only the cards the user dropped by hand moved to the place they named. A drop that is undone, or one whose named card has since left the lane, leaves the card in its own place.

A card's lane is the queue first, then the user's own placement, then the session's own history. `placementAt` is the moment of the drag and `placementBefore` names the card the dropped one sits in front of (`null` is the end of the lane) — nowhere in Done, which stores no arrangement; a real turn in the session or a queue lease that starts later outranks both, so the card returns to the lane its work belongs in and only a later drag moves it again. Build complete holds every Build turn that has settled: an idle Build session is finished history, and only a manual move puts its card in Done. The board's Build complete lane is a view of that state; it is not a stored stage.

The Build queue column renders server queue entries and live Build sessions in
the board's scope that have no queue entry. Queue entries take presentation
precedence for their session; a live-only build offers the queue-participation
action in the board. A live Build the queue adopted as the project's active
build is a lease, so it renders as the running build and holds the lane until
its turn ends. The column count follows rendered rows, including entries without
board cards.
An adopted build owns no queued item: the raw build snapshot omits `itemId`,
and the board projection sends `queue.active.itemId: null`. Both UI readers
accept this state; it offers no item-specific recovery controls.

`queue.paused` projects the directory's membership in the build snapshot's
`pausedDirectories`. It is independent of waiting rows' `paused` values, which
remain individual entry pauses. A failed queue read returns `known: false` and
disables the UI pause control; it cannot establish that the queue is running.
